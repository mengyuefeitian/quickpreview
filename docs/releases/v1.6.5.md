## v1.6.5 — 修复「播放大视频直接崩溃」

---

### 修复

#### 1. 播放 GB 级 mp4 时整个程序崩溃、托盘图标一起消失

反馈来自 [issue #5](https://github.com/mengyuefeitian/quickpreview/issues/5)。日志里三次崩溃
都发生在视频首包返回之后，`media.log` 记的是这样一行：

```
__local 206 xxx.mp4：Partial Content，1,975,618,907 字节（0–1,975,618,906 / 共 1,975,618,907）
```

播放器首包固定发 `Range: bytes=0-`（没有结束位）。本地文件服务当时按字面理解，
把**整个文件**塞进了一个响应体 —— 1.9GB。WebView2 需要吃下这么长的响应体，
浏览器进程被打爆，连带宿主在 `PInvoke.DispatchMessage` 抛 `SEHException` 直接退出。

对照同一台机器上的其它视频，规律很清楚：

| 文件 | 大小 | 结果 |
|---|---|---|
| 1.97 GB mp4 | 1.97 GB | 崩溃 |
| 1.32 GB mp4 | 1.32 GB | 崩溃（两次） |
| 同一个片子截取版 | 325 MB | 正常 |
| 另一个 mp4 | 57 MB | 正常 |
| 另一个 mp4 | 38 MB | 正常 |

分界线在 **GB 级**，与编码无关（325MB 那个同样是 H.265）。

现在单次响应最多 8MB，剩下的由浏览器继续发 `Range: bytes=<end+1>-`。
这对拖动进度条没有任何影响 —— 206 分片本来就是播放器的正常工作方式。
区间计算抽成纯函数 `FileRange.Resolve`，并配了 17 条离线断言
（GB 级首包 / 续包 / 末段不足一块 / 正好一块 / 越界收敛 / suffix / 多区间 /
空文件 / 200 全量不截断），跑 `python test-samples/dev_range_test.py` 可复现。

#### 2. 预览引擎崩了之后，宿主要跟着一起死

`SEHException` 会绕过 `Application.ThreadException`，一路冒到
`AppDomain.UnhandledException` —— 而那个处理器只能记日志、拦不住进程退出。
这就是「程序没了、还得手动重新启动」的原因。

现在消息循环外面接了一层自愈：接住异常 → 重建主窗体 → 气泡提示
「预览引擎异常退出，已自动恢复，该文件可能不受支持」。托盘图标和全局空格键继续可用，
10 分钟内最多恢复 3 次，避免真的坏掉时死循环。

#### 3. 退出路径上再记日志会抛 `ObjectDisposedException`

`Log.Shutdown()` 之后落盘线程已停、`_wake` 已释放，此时任何 `Log.E`
（崩溃自愈正要写日志）都会在异常处理里再抛一次，把进程带走。
现在停止写入之后改为同步落盘：这条日志既不会丢，也不会引发二次异常。

#### 4. `media.log` 看不到播放器到底要了哪一段

`__local` 记录里补上请求的 `Range` 原文；被分块时额外记一行
「本次 N 字节（客户端本可拿 M 字节）」。下次排查同类问题不用再靠猜。

### 说明

本次改动为纯修复，版本号按规则只递增第三位。**8MB 分块对 GB 级文件的首次加载
免不了多几次往返**，但换来的是不再崩进程 —— 相对代价可以忽略。
